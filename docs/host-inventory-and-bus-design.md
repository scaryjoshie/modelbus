# Com-Link Hub: Per-Host Adapter Inventory & Agent-Bus Design Reference (September 2026)

## TL;DR
- **Only Claude Code has a first-party, documented "push into a running session" mechanism** (the MCP `notifications/claude/channel` "Channels" feature, research preview, v2.1.80+), and even it is unreliable and TTY-oriented — every other host requires the hub to deliver via a pull/poll model (host acts as MCP client) or a headless-turn injection, so the hub must be **pull-first with push as a Claude-Code-only optimization**.
- Almost every coding-agent host **is an MCP client** (stdio + streamable HTTP), so the single most portable adapter to build is an **MCP server face** exposing a `sync()`/`check_inbox()` pull tool; wake-priority delivery then layers host-specific injection (Claude Code Channels, tmux paste, headless SDK turn, or `sessions_send`) on top.
- The ecosystem has already converged on the shape the hub proposes: SQLite-backed local buses with per-agent names, cursor/seq pull semantics, and explicit loop caps. Claude Code's own cross-session messaging **rate-limits repeated senders, drops identical repeats, and queues at most 50 accepted messages** — adopt these as hub defaults.

### Details and citations

**Claude Code (CLI) — the one host with a real push primitive.** "Channels" is an MCP server that declares the experimental capability `claude/channel` in its `Server` constructor and then emits `notifications/claude/channel` notifications, which Claude Code delivers into the running session wrapped in a `<channel source="…">` tag (code.claude.com/docs/en/channels-reference). It is **research preview, requires Claude Code v2.1.80+, requires claude.ai login (API-key/console auth unsupported), Team/Enterprise orgs must explicitly enable it, and during the preview only an Anthropic-curated allowlist of plugins can register** (custom servers need `--dangerously-load-development-channels`; Telegram/Discord/iMessage/fakechat ship in the preview). The transport is **stdio only** — Claude Code spawns the channel server as a subprocess. Key constraint for the hub: **Claude Code does not acknowledge notifications** — `mcp.notification()` resolves when written to the transport, not when Claude processes it, and "if the session hasn't loaded your server as a channel, or the organization policy blocks it, Claude Code drops the events silently and returns no error." Events queue and are delivered together on the next turn if Claude is busy. Two-way channels expose a reply tool; permission relay uses `notifications/claude/channel/permission_request` / `permission` with a five-lowercase-letter request ID (v2.1.234+ scopes relay to registered channels; v2.1.211+ sanitizes relayed fields to 3,500 code points; v2.1.234+ masks credentials). **Reliability is a real problem**: issue #36827 (Mar 20, 2026) reports Telegram-plugin `notifications/claude/channel` "sent successfully" but never delivered to the session; issue #45563 reports the same across sessions and asks Anthropic to clarify whether the capability is actually implemented, stating "the Channel feature provides zero value" when messages must still be manually pulled.

Hooks: Claude Code supports Stop, SessionStart, PreToolUse and related lifecycle hooks; critically, `CLAUDE_CODE_MESSAGING_SOCKET` is exported to hooks and Bash commands once the inbox socket binds (bound before any hook runs, including SessionStart). This makes a **hook-driven poller** a viable secondary injection path.

Native multi-agent messaging: cross-session `SendMessage`/`ListAgents` landed in **v2.1.224** (macOS/Linux incl. WSL2, not native Windows; not on Bedrock/Claude Platform on AWS/GCP Agent Platform/Microsoft Foundry). Same-machine delivery is a local UDS socket; each session binds an inbox socket and registers in on-disk files. v2.1.225 extended it so a session can *open* (not just reply to) a conversation with Remote Control sessions on other machines. `SendMessage` is the same tool used for subagents and agent-team teammates (denying it removes all three). In auto mode, messages are evaluated by the permission classifier before dispatch (v2.1.222, Aug 4, 2026). Loops are throttled (see Part 3).

**Claude Agent SDK.** Streaming input mode is "the preferred way to use the Claude Agent SDK … allows the agent to operate as a long-lived process that takes in user [messages]" via an async generator of `SDKUserMessage` objects (docs.claude.com/en/docs/agent-sdk/streaming-vs-single-mode). This is the hub's cleanest headless injection point for an SDK-hosted agent: feed a new user turn into the generator whenever a wake-priority message arrives. The SDK connects MCP servers, supports hooks, and runs the CLI under the hood.

**OpenAI Codex CLI.** No push-into-session mechanism. Headless is `codex exec "…"` (with `--json`, `-o`, `--output-schema`, `--full-auto`), and a turn can be appended with `codex exec resume --last "…"` or by session UUID/name (DeepWiki openai/codex 4.2, 4.2.2). Codex is an MCP client (`codex mcp add <name> <command>`, `codex mcp list`) and ships its own `codex-mcp-server` so other clients can drive it. Injection path = spawn/resume an exec turn.

**Cursor (Agent CLI + editor).** Cursor CLI is an MCP client (`agent mcp list`, `agent mcp list-tools`, `--approve-mcps`) with a headless print mode (`agent -p`, `--output-format json`). It also exposes a hidden `agent acp` subcommand — "intended for custom ACP clients and advanced integrations … hidden from default command help output" (cursor.com/docs/cli/reference/parameters). MCP-in-headless is finicky: `cursor-agent -p` failed to use a configured MCP where `--force` worked (forum.cursor.com/t/136709). The editor agent is a GUI MCP client with no external push API. Cursor's ACP is Zed's Agent Client Protocol (it runs inside JetBrains/Android Studio via the CLI bridge).

**Gemini CLI.** MCP client since first release: stdio plus remote SSE/HTTP with OAuth 2.0 discovery; `/mcp` slash commands; server "instructions" appended to the system prompt (github.com/google-gemini/gemini-cli docs). No push, limited hooks. **Caveat:** Gemini CLI docs now warn it "will be replaced by Antigravity CLI on June 18th" for unpaid/One-tier users — treat as potentially deprecating and plan an Antigravity adapter.

**OpenCode.** `opencode serve` runs a headless HTTP server exposing an OpenAPI 3.1 spec (`/doc`), with optional HTTP basic auth (`OPENCODE_SERVER_PASSWORD`, user `opencode`) and CORS (opencode.ai/docs/server). It has a `/tui` endpoint that "can be used to drive the TUI through the server. For example, you can prefill or run a prompt" — a genuine external injection surface. OpenCode is an MCP client (local + remote, auto-OAuth) and also exposes an **ACP server** over stdin/stdout ND-JSON. The `opencode serve` HTTP API is the recommended adapter.

**Zed (via ACP).** Zed integrates external agents through **Zed's Agent Client Protocol (ACP)** — an editor↔agent standard (Apache-2.0), distinct from IBM/BeeAI's Agent Communication Protocol. Zed hosts the thread; the external agent (Claude, Codex, Gemini CLI, OpenCode, Copilot, Cursor) owns its runtime, auth, and model, installed via the ACP Registry (`zed: acp registry`). For the hub, Zed itself is not a push target; the *agent* behind ACP is (via its own mechanism).

**Aider.** Recent builds add an **stdio MCP client** (config via `.aider.conf.yml` `mcp-server:` or flags; supports tools + prompts) but there is no native MCP server or Agent Mode in core Aider — an open feature request (#4506) asks for `aider --mcp-server`. Aider is scriptable via CLI and Python. No push, no hooks, no native multi-agent messaging. Third-party AiderDesk adds full agent mode + MCP.

**GitHub Copilot CLI / coding agent.** Copilot CLI is an MCP client supporting local/STDIO and remote HTTP (streamable) + legacy SSE (docs.github.com), ships the GitHub MCP server by default, supports **hooks** ("run custom shell commands automatically at key points during a CLI session"), subagents/custom agents, autopilot mode, and steering. The Copilot **coding agent (cloud)** supports MCP **tools only** — not resources or prompts, and not remote OAuth MCP servers (docs.github.com mcp-and-coding-agent). No push into a running local session.

**Cline / Roo Code.** Cline is an MCP client with stdio and streamable HTTP/SSE (`"type":"streamableHttp"`), a **hooks system**, headless CLI mode (`-y/--yolo/--no-interactive` for CI), an **ACP server** for editor integration, an SDK with lifecycle hooks, and coordinator→specialist multi-agent workflows (github.com/cline/cline; docs.cline.bot). Enterprise remote config can enforce MCP allowlists. Roo Code (fork) is a VS Code-bound MCP client; one source states Roo Code shut down in May 2026 — verify before building an adapter.

**Goose (Block).** MCP-native (every capability is an MCP extension); headless via `goose run --no-session -t "<text>"`; subagents via sub-recipes; Apache-2.0. Per the Linux Foundation press release of December 9, 2025, "the Linux Foundation … today announced the formation of the Agentic AI Foundation (AAIF), and founding contributions of three leading projects … Anthropic's Model Context Protocol (MCP), Block's goose, and OpenAI's AGENTS.md" (the goose repo/governance transferred from Block to AAIF in April 2026). No push; injection = spawn a headless run. `mcp-goose` (adamd9) wraps the CLI so other agents can start/poll jobs.

**Hermes Agent (Nous Research).** Python self-improving agent (github.com/NousResearch/hermes-agent) with a messaging gateway across 20+ chat platforms, an OpenAI-compatible server, isolated subagents, and ACP/IDE support. Core has **no first-class agent-to-agent bus**; A2A is plugin/community territory: `hermes-bus-plugin` (mlinquan) auto-starts a bus daemon and **injects external messages via a `pre_llm_call` hook**, exposing `bus_send`/`bus_status`/`bus_info`; a proposed official "Agent Message Bus" (SQLite + MCP tools + cron, github.com/kriszmac4/a2a-communication-protocol) was declined for core (issue #42349, not-planned). For the hub, the `pre_llm_call` injection pattern is the model to emulate.

**OpenClaw (gateway).** OpenClaw's gateway provides `sessions_send` (deliver into a session) and `sessions_spawn` (create/resume a session, including `runtime:"acp"` via the embedded **acpx** ACP backend plugin). ACP sessions run on the host runtime (not inside OpenClaw's sandbox); OpenClaw still enforces feature gates, allowed agents, session ownership, channel bindings, and delivery policy (docs.openclaw.ai/tools/acp-agents). The ACP runtime is buggy: `ACP_TURN_FAILED` after gateway restart (#76564); model-passthrough failure when a harness lacks `session/set_model`, e.g. OpenCode (#95869); opaque `ACP_TURN_FAILED` on spawn (#31065); ACP output not persisted so `sessions_history` returns empty (#29593); and no steer/action support for ACP runtime sessions (#43496). For the hub, `sessions_send` is the native push; treat ACP-runtime as unreliable.

**Browser-based agents.** *Claude in Chrome* is exposed to Claude Code as an MCP server named `claude-in-chrome` (`claude --chrome`, `/chrome`); it drives your real browser session and can "open localhost:3000 … check the console for errors" — i.e. it **can navigate to a localhost HTTP endpoint and read a localhost page** (code.claude.com/docs/en/chrome). It is not itself a push target, but a hub could expose a localhost page/endpoint the browser agent reads on demand. *Playwright-MCP / Browser Use* agents are driven via MCP and can navigate to localhost too. *OpenAI Operator / ChatGPT agent* runs in a cloud sandbox and **cannot reach your localhost** or accept a local MCP connection — effectively unreachable by a local hub.

### Details and citations

The dominant pattern is unmistakable: **a local SQLite (or file) store, an MCP stdio face, per-agent names, pull via poll/cursor, and explicit-recipient addressing.** Agent Bus MCP (github.com/alessandrobologna/agent-bus-mcp) is the closest match to the hub's design intent — "a stdio MCP server backed by SQLite. Agents create named topics, join with stable peer names, send and receive messages through `sync()`, and resume from server-side cursors," plus a local Web UI for browsing/searching/exporting. Its rationale ("Multi-agent coding breaks down when every tool keeps its own memory … the coordination ends up in pasted summaries") is exactly the problem the hub targets.

MCP Agent Mail (Dicklesworthstone) contributes the most explicit **anti-spam and robustness lessons**: "Explicit recipients only. `send_message` keeps a broadcast field for schema compatibility, but `broadcast=true` is intentionally rejected so agents cannot spam every other agent by default"; "Project isolation first"; "TTL instead of forever-locks … robust to crashed or vanished agents"; "Wrong-surface denial. MCP-only and CLI-only commands fail deterministically when invoked through the wrong entrypoint." The Rust rewrite adds a TUI and 34 tools with symmetric glob overlap for file reservations.

claude-peers-mcp (jamditis, building on louislva's original) is the most instructive for **wake-priority delivery and loop avoidance**: a broker daemon on port 7899 with SQLite; each Claude session spawns an stdio MCP server registering its tmux pane; messages are delivered by bracketed-paste `tmux send-keys` into the pane, or queued if no pane. Its urgency model directly informs the hub's priority tiers: "Each message carries an urgency tier that maps to a `push_after` deadline: interrupt is push-due immediately; normal waits `push_delay_ms` (default 2 minutes) so the recipient can drain it cheaply." It also "probes the pane's foreground process: if it is a bare shell rather than a live Claude session, the message is held queued instead of pasted," and a wedged session is escalated to a louder log — a concrete backpressure guard. Broker/MCP negotiate a protocol version (v4). The JasonDictos "network-claude-peers-mcp" fork extends this across a LAN with token auth and durable mailboxes.

postal-mcp (tkellogg) is the notable **HTTP-only** design: `send_message`/`check_mailbox` (blocking), agent name embedded in the URL path (`/agents/gemini/mcp`), so the same SQLite queue is always shared — but the author notes it "doesn't return to the mailbox easily," a lesson about blocking-check ergonomics. AMQ (avivsinai) is the **file/Maildir** design with a dead-letter queue and strict root-pin refusal.

agent-bridge (raysonmeng, aka "claude_codex_bridge") is the clearest **implemented loop-prevention** example outside Claude's own: "Loop prevention via the per-message `source` field," plus "a busy-guard [that] rejects replies during an active Codex turn" and "a per-turn inactivity watchdog [that] stops a lost turn/completed from locking injection forever." mcp-dispatch (sophia-labs) contributes **piggyback delivery** (attach pending messages to every tool response, avoiding polling) with a `default_ttl` and `max_message_bytes` = 65536 cap.

**Not buses (flag):** muster (giantswarm, Go) is an MCP aggregator/control plane on Kubernetes CRDs with streamable-HTTP on :8090 and OAuth 2.1 + PKCE — useful as a transport reference, not an A2A mailbox. claw-orchestrator (Enderfga, TypeScript) unifies many CLIs into one runtime with an MCP server and ACP agent but documents no loop protection. "tutti" is an ambiguous name across ≥3 unrelated projects (nutthouse tmux orchestrator with a `:4040` SSE dashboard; tutti-os shared workspace ~2,004★ per a third-party aggregator, unverified; tuttiai TS SDK with Postgres). **Could not verify** repos named exactly "interlink-mcp" or a "mcp-use notification-test channels demo"; closest are QuentinCody/interlinked-cli (lease-based file reservation, 5-min TTL, 30-sec idle auto-release) and generic MCP notification demos. GitHub star counts and last-commit dates were not reliably capturable for most projects and should be verified at build time.

## PART 3 — Loop protection and idle-notification patterns

**Claude Code cross-session messaging (the primary published numbers).** Per the Claude Code docs (code.claude.com/docs/en/cross-session-messaging): "Claude Code rate-limits repeated messages per sender, drops identical repeats arriving within a short window, and queues at most 50 accepted messages for Claude to read. A message loop between two sessions therefore stops on its own." It also holds "at most 100 messages, separately from the delivery queue, and past that drops the oldest." A newer guard (v2.1.236) "refuses further messages up front once a rapid burst would exceed what the recipient's inbox accepts, instead of reporting them sent while the recipient dropped them." A non-interactive `claude -p` session can receive but not approve (no dialog), so a held message stays held unless `crossSessionInbound: "accept"` is set; bare mode skips the socket entirely. In auto mode, `SendMessage` calls are evaluated by the permission classifier before dispatch (v2.1.222, Aug 4, 2026).

**Claude Code agent teams — idle notifications & shutdown_request (the reported problem area).** Agent teams (behind `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1`) use a protocol including `idle_notification`, `shutdown_request`/`shutdown_response`, and hooks `TeammateIdle`/`TaskCreated`/`TaskCompleted` (code.claude.com/docs/en/agent-teams): "when a teammate finishes and stops, it automatically notifies the lead and includes its final answer in the notification"; "the lead sends a shutdown request. The teammate can approve, exiting gracefully, or reject with an explanation"; and `TeammateIdle` "runs when a teammate is about to go idle. Exit with code 2 to send feedback and keep the teammate working." The runtime reviews each message (including structured shutdown/plan-approval messages) before delivery. **Reported failure modes**: issue #85047 (Aug 8, 2026) — "idle-notification ping-pong": acknowledging a finished teammate wakes it and emits another `idle_notification`, "up to three 'I'm done' style notifications per agent," with proposed fixes to dedupe idle notifications and add a "release/ack" send that doesn't wake the teammate; sending a plain-text farewell instead of a formal `shutdown_request` is the anti-pattern that re-triggers the loop. Issue #79016 (Claude Code v2.1.210) — finished teammates linger idle indefinitely with no bulk dismiss; shutting down 21 agents took 21 handshakes and one agent "repeatedly ignored the pending shutdown_request and only emitted idle_notification" until sent an explicit `shutdown_response` JSON. Issue #38116 (Mar 24, 2026, closed not-planned) — `TeamDelete` fails with "active members" not cleared and "agents continue sending idle_notification after termination." **Lesson for the hub: dedupe idle/status messages, provide an ack that does not wake, and use an explicit terminate rather than a chatty farewell.**

**OpenClaw.** OpenClaw's published loop protection is a **tool-call loop detector** (`tools.loopDetection`), not a dedicated agent-to-agent hop counter (docs.openclaw.ai/tools/loop-detection). Two guardrails: (1) loop detection, **disabled by default** (`enabled: false`), which "watches the rolling tool-call history for repeated patterns and unknown-tool retries"; and (2) a post-compaction guard, on unless explicitly false, which "aborts the run if the agent repeats the same `(tool, args, result)` triple within the window," emitting `compaction_loop_persisted`. For message loops specifically: "Outbound message-send results are hashed with volatile per-call ids (message id, file id, timestamp) stripped, so a 'sent' result does not look identical to a different 'sent' result." Escalation is warn-then-block. No published numeric TTL/hop-count/budget-cap for agent-to-agent forwarding was found — the recommended control for runaway agents is spawning isolated bounded sub-agents.

**Hub-side patterns actually implemented across projects.** Concrete, shipped mechanisms: per-message `source`/sender field to detect and drop self-echo (agent-bridge); busy-guard rejecting delivery during an active turn + per-turn inactivity watchdog (agent-bridge); urgency tiers mapping to push deadlines so "not every message interrupts," with a default 2-minute delay for normal priority and immediate for interrupt (claude-peers-mcp); holding a message if the target pane is a bare shell and escalating a wedged session (claude-peers-mcp); TTL on messages/leases so crashed agents don't hold state (mcp-dispatch `default_ttl`, MCP Agent Mail reservations, interlinked-cli 5-min/30-sec); a byte cap `max_message_bytes` = 65536 (mcp-dispatch); and unread-queue cap of 50 + identical-repeat drop + repeated-sender rate-limit + burst-refusal (Claude Code). **These are the concrete defaults to adopt.**

## PART 4 — Standards status check (September 2026)

**A2A.** A2A reached **v1.0 (first stable, production-ready spec) in March 2026** (a2a-protocol.org), with signed Agent Cards for verifiable identity and SDKs across five languages. Google donated A2A to the Linux Foundation in June 2025 (with AWS, Cisco, Microsoft, Salesforce, SAP, ServiceNow). **IBM/BeeAI's Agent Communication Protocol was merged into A2A on Aug 29, 2025** (LF AI & Data blog, "ACP Joins Forces with A2A"); the ACP repo (github.com/i-am-bee/acp) was archived read-only on Aug 27, 2025 with its README now stating "ACP is now part of A2A," and IBM's Kate Blair (Director of Incubation) joined A2A's Technical Steering Committee alongside Google, Microsoft, AWS, Cisco, Salesforce, ServiceNow, SAP. On **Aug 17, 2026, A2A became a hosted project of the Agentic AI Foundation (AAIF)** under the Linux Foundation, alongside MCP. So "IBM ACP fully merged" = **yes**. The separate AGNTCY Agent Connect Protocol also archived (Apr 11, 2026) recommending A2A. (Adoption figures — "150+ organizations in production," "250 members" — are from the foundation/vendor announcements, not independent measurement.)

**MCP spec.** The current spec is **2026-07-28** (final, published on schedule, three weeks before A2A joined AAIF), the largest revision since launch, making MCP **stateless at the protocol layer**: per the changelog, it "remove[s] protocol-level sessions and the Mcp-Session-Id header from the Streamable HTTP transport. List endpoints (tools/list, resources/list, prompts/list) no longer vary per-connection. Servers that need cross-call state use explicit, server-minted handles passed as ordinary tool arguments (SEP-2567)." **Streamable HTTP** now "requires Mcp-Method and Mcp-Name (SEP-2243)" so gateways/rate-limiters can route without parsing bodies; "responses from tools/list, prompts/list, resources/list, and resources/read now carry ttlMs and cacheScope (SEP-2549)." **Server-initiated notifications** moved from the old HTTP GET endpoint to a single `subscriptions/listen` stream that clients opt into per notification type. **Async work ("Tasks")** shipped experimentally in 2025-11-25 (call-now/fetch-later: server returns a taskId, client polls) and in 2026-07-28 moved out of core into the `io.modelcontextprotocol/tasks` extension with poll-based `tasks/get` + `tasks/update` (SEP-2663). Roots/Sampling/Logging are deprecated (SEP-2577, 12-month offramp); legacy HTTP+SSE is deprecated. Native webhook/callback ("Triggers and Event-Driven Updates") remains **only "On the Horizon," not in the spec** — reinforcing that server→session push is not yet standardized and Claude Code's Channels is a proprietary extension.

**De facto lightweight-chat envelope.** No standard beyond A2A's Message/parts shape has emerged. The community buses split between **plain-string content** (Claude Code cross-session messages are deliberately thin text; agent-bus; postal-mcp) and **typed/threaded envelopes with metadata** (MCP Agent Mail threads + leases; claude-peers-mcp urgency tiers; mcp-dispatch state machine). Claude Code's Channels envelope (`content` string + `meta` string-map rendered as `<channel>` tag attributes) is the closest thing to a widely-copied push envelope. **Recommendation: mirror A2A's Message/parts for the wire envelope (future-proofing) while keeping a plain-string fast path, since real agents consume text.**

### Overall architecture recommendation
Build the **MCP server face first** — it is the universal pull adapter (`sync()`/`check_inbox()` with server-side cursors) that every MCP-client host works with. Under the 2026-07-28 stateless spec, pass session state as explicit tool-arg handles (no `Mcp-Session-Id`), emit `Mcp-Method`/`Mcp-Name` on Streamable HTTP, and use `subscriptions/listen` for opt-in change streams. Layer **push adapters** only where a host supports them: Claude Code Channels (with tmux/socket fallback), Agent SDK streaming input, OpenCode `/tui`, OpenClaw `sessions_send`, and hook/`pre_llm_call` injection for Copilot/Cline/Hermes. 

Enforce **hub-side loop protection by default**, borrowing the numbers that shipping projects already use: a per-message source/sender field for self-echo drop; identical-repeat dedupe within a short window; an unread-queue cap (start at **50**, per Claude Code, with a separate ~**100** overflow drop-oldest); urgency tiers with a normal-priority push delay of **~2 minutes** and immediate interrupt (per claude-peers-mcp); a **hop counter + TTL** on relayed messages (no host publishes a hop count, so this is a hub-original guard — recommend a default max of 4–8 hops and a message TTL of a few minutes); a busy-guard that holds delivery during an active turn; and a per-message byte cap of **~64 KB** (per mcp-dispatch). Mirror A2A's Message/parts envelope on the wire while keeping a plain-string fast path.
